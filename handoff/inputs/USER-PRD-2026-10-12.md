# DevEnvCorpus — Lightweight PRD

**Status:** Draft
**Purpose:** Turn published research on developer-environment threats into a source-linked, structured dataset that supports comparison, investigation and later TTP mapping.

## 1. Problem

Relevant research is scattered across blog articles, incident reports and technical walkthroughs. Reports use different terminology, several sources may describe the same campaign, and reported observations can become mixed with interpretation.

DevEnvCorpus will organize this research consistently while preserving source attribution and uncertainty.

## 2. Initial scope

The first release will:

- Ingest article URLs or supplied text.
- Extract publication metadata and relevant passages.
- Produce structured, source-linked summaries.
- Categorize affected trust surfaces and AI involvement.
- Group related reports under a campaign or incident.
- Support filtering, timelines and qualitative cross-case observations.
- Require review before extracted claims become accepted dataset records.

Attack-path reconstruction and MITRE ATLAS mapping are later enrichment stages. They are not prerequisites for collecting useful research.

## 3. Users and workflows

**Security researchers** collect sources, review extracted claims and compare campaigns.

**Detection and DFIR practitioners** identify reported behaviors, evidence to seek and potential detection opportunities.

**Research agents** query reviewed records, retrieve supporting passages and propose enrichment for human review.

Primary workflow:

**Add source → extract draft → categorize → review → link to case → compare and enrich**

## 4. Data model

Keep **sources, cases and claims separate**. One case can have several sources; one source can describe several cases.

| Entity | Required fields |
|---|---|
| **Source** | Source ID, original URL, canonical URL, title, publisher, author when available, publication date, retrieval date, content hash, extraction status |
| **Case** | Case ID, name, aliases, concise summary, linked source IDs, review status |
| **Claim / behavior** | Claim ID, case ID, behavior description, source ID, supporting passage and location, evidence status, reviewer disposition |
| **Categorization** | Trust surfaces, AI involvement, execution locations, affected tools/platforms, tags |
| **Timeline entry** | Event description, date or range, date precision, date type, supporting claim/source |
| **Future TTP mapping** | Behavior ID, framework and version, technique ID or candidate label, rationale, supporting claims, mapping status |

Unknown values remain null. The system must distinguish **unknown**, **not reported** and **not applicable**.

## 5. Categorization

Categories are multi-label. A campaign can cross several trust surfaces.

### Developer trust surfaces

- Social engineering and malicious repositories
- Package or registry compromise
- IDE and local execution paths
- Skill marketplace poisoning
- MCP or tool poisoning
- Credentials and identity
- CI/CD and cloud

**Attacker-side AI use is an operating role, not a developer trust surface.**

### AI involvement

| Label | Meaning |
|---|---|
| **Victim-side agent abuse** | An attacker attempts to influence or abuse AI tooling in the victim environment |
| **Attacker-side AI use** | An attacker uses AI tooling to develop, coordinate or execute operations |
| **AI review targeting** | Malicious content attempts to influence an AI scanner, reviewer or analysis system |
| **AI assets targeted** | AI credentials, sessions, configurations or access are theft or compromise targets |
| **No AI involvement reported** | The reviewed source does not describe AI involvement |
| **Unclear** | Available evidence does not support a reliable classification |

Allow several labels per case. Record which behavior supports each label.

### Additional dimensions

- **Execution location:** endpoint, IDE, CLI, WSL, container, CI runner, cloud, remote service, unknown
- **Delivery mechanism:** recruiter lure, repository content, package install/update, extension, Skill, MCP integration, configuration change, other
- **Reported objective:** credential theft, data theft, persistence, execution, lateral movement, disruption, other/unknown
- **Evidence to seek:** native agent records, endpoint telemetry, package provenance, repository/CI records, identity/cloud logs, network records

## 6. Evidence and review

Every substantive claim must have a supporting passage or an explicit **researcher inference** label.

Evidence status:

- Source-reported observation
- Attempted behavior
- Demonstrated capability or proof of concept
- Potential consequence
- Researcher inference
- Unclear or disputed

Review status:

- Collected
- Extracted — review pending
- Reviewed
- Needs correction
- Excluded

Preserve conflicting claims separately. Do not silently merge them into a single conclusion.

## 7. Timelines and overlapping observations

Keep these dates distinct:

- Publication and source-update dates
- First reported activity
- Incident or execution date
- Discovery date
- Disclosure date

Support approximate dates and ranges, such as a year or month. Do not substitute publication date for incident date.

Cross-case comparison should identify shared categories, behaviors, tooling and delivery mechanisms. Label outputs as **observations within the collected dataset**.

Any counts must show the counting unit, filters and review coverage. Multiple reports about one campaign must not inflate campaign counts. Similar behavior does not establish shared attribution or infrastructure.

## 8. MITRE ATLAS and new TTP enrichment

A later enrichment stage will propose mappings from reviewed behaviors.

Requirements:

- Store the framework version and exact technique identifier.
- Provide a mapping rationale and supporting claims.
- Allow multiple mappings or no mapping.
- Keep proposed mappings separate from reviewed mappings.
- Support other frameworks where ATLAS does not fit the behavior.
- Never force a conventional supply-chain behavior into an AI-specific technique.

Unmapped behaviors can become **candidate emerging TTPs**, with a provisional name, definition, examples and related techniques. They must not be presented as official MITRE techniques.

## 9. MVP product requirements

1. **Source intake:** Accept URLs and pasted/uploaded text; retain provenance and report extraction failures.
2. **Structured extraction:** Generate records against a versioned schema with passage-level support.
3. **Case linking:** Suggest duplicate sources and related cases; require review for uncertain merges.
4. **Review interface:** Show source passages beside extracted fields and allow correction.
5. **Search and comparison:** Filter by category, AI involvement, dates, tool, evidence status and review status.
6. **Export:** Provide JSONL for structured records and CSV views for cases, sources and timelines.
7. **Traceability:** Preserve record IDs, revisions, reviewer decisions and extraction/model versions.

## 10. Acceptance criteria

The MVP is ready when:

- Every accepted behavior is traceable to a source passage or labeled inference.
- Unsupported fields remain unknown rather than fabricated.
- A case can retain multiple sources and conflicting claims.
- AI involvement and trust surfaces support overlapping labels.
- Publication dates and activity dates remain distinguishable.
- Duplicate articles do not create duplicate campaign counts.
- Exports validate against the declared schema.
- AI-extracted records remain review pending until accepted.

Use a small, varied evaluation set covering victim-side agent abuse, attacker-side AI use, AI review targeting and conventional developer attacks.

## 11. Non-goals

The initial release will not claim exhaustive threat coverage, measured ecosystem prevalence, validated detection coverage or successful incident replay. It will not automatically execute reported attack commands or generate authoritative attribution.

## 12. Delivery stages

**Stage 1 — Collection:** Source intake, extraction, case records, categorization, review and export.

**Stage 2 — Comparison:** Related-case linking, timelines, overlapping behaviors and source-supported observations.

**Stage 3 — Enrichment:** Reviewed framework mappings, candidate emerging TTPs and optional attack-path or detection-opportunity analysis.
